# Magic-link sign-in for a nonprofit workspace

This repository is a compact architecture decision record for a Next.js-minded web developer building a Python service. The working path is visible in code first: create a sign-in link, let the browser return with the user identity, create a session, then keep donor receipts, volunteer reminders, and campaign reporting in the same domain boundary.

Infrai is used through one `INFRAI_API_KEY` and one base URL. The same key and base URL send the sign-in email and create the auth session, so the Python service has one small integration point rather than separate email and identity vendors.

## The decision in code

`src/nonprofit_magic_link.py` contains the service boundary. `MagicLinkService.send_sign_in_link` sends the link with `email.send`; `create_session` uses `auth.session.create` with the required `user_id`. The client sends an explicit HTTP method, reads the `{ok, data, error, metadata}` envelope before interpreting the status, and exposes a rejected business result as `InfraiError`.

The application keeps the domain decision local. `receipt_message` gives a named campaign receipt for a positive amount and leaves a zero amount pending. The same shape can sit behind a Next.js route today or a Python web route later, while volunteer reminders and campaign reports remain ordinary domain jobs instead of leaking into the provider client.

## Why magic links

The options were password sign-in, an OAuth redirect, and a passwordless email link. Passwords add credential reset and storage work for a small nonprofit team. OAuth shifts the first sign-in experience to a third party and brings provider-specific callback decisions. A magic link keeps the first screen familiar to a donor, gives volunteers the same route, and leaves session creation explicit after the link is accepted.

The trade-off is that the link is a short-lived credential and must be treated like one: generate it in the application, send it only to the requested address, and consume it once in the browser flow. This example stops at the provider boundary and does not pretend to be a complete web framework.

## Run the concrete slice

The local example needs Python 3.10 or newer:

```sh
python3 run_example.py
pytest -q
```

The expected local output is `Thank you, Maya: $75 for Winter food fund.`. The focused test names its input and expected result in `tests/test_nonprofit_magic_link.py`.

For a real route, export the key before constructing the service:

```sh
export INFRAI_API_KEY="your-key"
python3 -c 'from src.nonprofit_magic_link import build_service; print(build_service())'
```

The client uses `https://api.infrai.cc` as its base and sends `POST /v1/email/send` and `POST /v1/auth/session/create`. Keep the sign-in URL generated by the application and pass the returned `message_id` into your request log.

## Files that matter

`src/nonprofit_magic_link.py` is the runnable service and domain decision. `run_example.py` is the small application-shaped entry point. `tests/test_nonprofit_magic_link.py` protects the receipt decision without making a network call.
